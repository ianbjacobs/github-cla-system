# Troubleshooting

## The Sign Contributor Agreement option is missing

- Confirm Issues are enabled under **Settings → General → Features**.
- Confirm `.github/ISSUE_TEMPLATE/sign-contributor-agreement.yml` exists on the repository's default branch.
- Confirm the Issue Form YAML is valid.
- Confirm all labels named in the form already exist.

Issue Forms are loaded from the default branch, even when the contributor pull request targets another branch.

## A signing issue does not create an Agreement pull request

- Confirm the issue has the exact `pending-agreement` label.
- Confirm `.github/workflows/create-agreement-pr.yml` is on the default branch.
- Inspect the **Create Agreement PR** workflow run.
- Confirm Actions has read/write permission and may create pull requests.
- Confirm the Issue Form's two required acknowledgements were checked.
- Confirm the target branch named in the issue exists in the repository.

## The Agreement pull request targets the wrong branch

The signing issue should contain a **Target branch** field. When the issue is opened from a managed pull-request comment, that field should be prefilled with the contributor pull request's base branch.

Check that:

- the current Issue Form on the default branch contains the `target_branch` field;
- the signing link was generated by the current `check-contributor-agreement.yml` workflow;
- the contributor did not alter the prefilled branch value;
- the current `create-agreement-pr.yml` and branch resolver are present on the default branch.

Old signing links or issues created before an update may still fall back to the default branch. Test branch-related fixes with a fresh contributor pull request and a fresh signing issue.

## The Agreement pull request waits forever for Contributor Agreement

Generated Agreement pull requests are opened with GitHub's workflow token, which may suppress a follow-up pull-request event. The **Create Agreement PR** workflow therefore publishes the green `Contributor Agreement` status directly on the generated pull request.

Confirm the workflow includes `statuses: write` and that its **Publish Agreement PR exemption status** step succeeded.

## GitHub asks a maintainer to approve workflows

GitHub may require approval before running workflows on a newly created or externally sourced pull request. Use the **Approve and run** or **Approve workflows to run** control after reviewing the proposed changes.

Approval of an old run does not load newer workflow code. To test a workflow change, create a new event—such as a new commit, a reopened pull request, or a fresh signing flow.

## An unsigned pull request has a green Actions job

The job named `Evaluate contributor agreement` can execute successfully while publishing a failing commit status.

The ruleset must require this exact status:

```text
Contributor Agreement
```

Do not use only the Actions job name as the merge gate.

## Contributor Agreement remains pending

A pending status normally means no workflow published it for the current head commit.

Check:

- whether the pull-request workflow ran for the current commit;
- whether workflows are waiting for maintainer approval;
- whether a generated Agreement pull request used the direct status-publication step;
- whether the ruleset requires the exact `Contributor Agreement` context;
- whether the workflow has `statuses: write` permission.

## The original pull request does not turn green after signing

Inspect **Refresh Contributor Agreements**.

The workflow should run whenever `CLA_REGISTRY.yaml` changes and should process the branch on which the registry was updated. Confirm:

- the workflow was not skipped by a default-branch-only condition;
- it checked out `${{ github.ref_name }}`;
- it passed the same branch as `TARGET_BRANCH`;
- the original pull request targets that branch;
- the new registry entry contains the contributor's numeric GitHub user ID.

The workflow currently evaluates up to the first 100 open pull requests returned by GitHub for the target branch.

## The signing comment does not disappear

First reload the pull-request page; GitHub's interface can lag behind API updates.

If the comment remains:

- confirm the `Contributor Agreement` status is green;
- inspect the latest **Refresh Contributor Agreements** run;
- confirm that run found the original pull request;
- confirm the workflow has `issues: write` permission;
- confirm the managed-comment marker was not manually removed from the comment body.

## The signing issue remains open

The `Close Signing Issue` workflow explicitly closes the originating issue after a labeled Agreement pull request is merged. This works even when the Agreement pull request targets a non-default branch.

If the issue remains open:

- allow a short delay and reload the page;
- confirm the Agreement pull request was merged rather than merely closed;
- confirm it had the `agreement` label at merge time;
- inspect the **Close Signing Issue** workflow run;
- confirm the head branch follows `agreement/<github-id>/issue-<number>`;
- confirm the workflow has `issues: write` permission.

The `Closes #<number>` text in the Agreement pull request remains useful for linkage, but GitHub's native closing-keyword behavior alone is not reliable for non-default branches.

## A workflow run was skipped

Open the workflow file and inspect any job-level `if:` condition. A condition that compares `github.ref` only with the repository default branch will skip registry refreshes on other protected branches.

For branch-aware registry refresh, the workflow must accept branch pushes and operate on `github.ref_name`.

## Direct pushes are rejected

A ruleset that requires pull requests blocks direct pushes, including pushes from repository owners unless they are allowed to bypass the ruleset.

Options:

- create a feature branch and open a pull request;
- add a temporary, tightly controlled bypass for repository administrators;
- remove the bypass after setup or repair work is complete.

Signing the CLA does not bypass a rule requiring pull requests.

## The Issue Form label is missing

Issue Forms apply only labels that already exist. Create `pending-agreement` manually in **Issues → Labels**, then open a fresh signing issue. Adding the label to an old issue does not recreate its original `opened` event.

## Local checks fail only on formatting

Run:

```bash
npm run format
npm run check
```

Commit formatter changes to the pull request's head branch. Updating only the base branch does not change the code being validated in an existing pull request.

## A rerun still uses old workflow behavior

Rerunning an existing Actions job uses the original event and workflow context. After changing workflow code, create a new event instead of repeatedly rerunning the old job.
